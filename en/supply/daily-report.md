# Daily Report API

**For:** SSP partners reconciling delivered impressions and billing against RevoSurge.

A read-only HTTP endpoint that returns one row per UTC day with bid, win, bill,
and impression counts, plus revenue and average CPM (USD) for your SSP. The
numbers come from the same data RevoSurge uses for its own reporting.

## Endpoint

```
GET https://rtb.revosurge.com/api/v2/ssp/{sspId}/report?from=YYYY-MM-DD&to=YYYY-MM-DD
Authorization: Bearer <jwt>
```

The `{sspId}` path variable **must** equal the `sub` claim in your token.
A leaked token still requires knowing the exact `sspId` to read data, and a
token can only ever return data for one SSP.

::: tip Report URL ≠ bid URL
This is not your bid endpoint (`/api/v1/openrtb2/...`). The bid endpoint
receives OpenRTB bid requests; this endpoint returns reporting data.
:::

### Passing the token

Two transports are accepted ([RFC 6750](https://www.rfc-editor.org/rfc/rfc6750) §2.1 and §2.3):

| Transport | Example | Notes |
|---|---|---|
| `Authorization` header | `Authorization: Bearer <jwt>` | **Preferred** |
| `access_token` query param | `...&access_token=<jwt>` | Fallback for tools that cannot set headers |

If both are supplied, the header wins. Query-string tokens can end up in proxy
and browser logs — prefer the header where you can.

## Authentication — tokens are issued by RevoSurge

Tokens are **generated by the RevoSurge platform team** and delivered to you.

- The signing secret is **internal** and never shared with partners.
- Do **not** attempt to sign your own tokens.
- A token has **no expiry**. It is valid until the secret is rotated, at
  which point we will issue you a fresh token.
- One token = one SSP id. See
  [Which traffic does my SSP id cover?](#which-traffic-does-my-ssp-id-cover)

See [How to obtain a token](#how-to-obtain-a-token).

## Parameters

| Param | Where | Format | Notes |
|---|---|---|---|
| `sspId` | path | string | Must match your token's `sub` claim |
| `from` | query | `YYYY-MM-DD` | UTC date, inclusive |
| `to` | query | `YYYY-MM-DD` | UTC date, inclusive. Today's partial day is allowed |
| `Authorization` | header | `Bearer <jwt>` | Your assigned JWT (or use `access_token`) |
| `access_token` | query | string | Optional. Only used when the header is absent |

Window constraints:
- Inclusive: `[from, to]`
- Maximum: **7 days** (`to - from <= 6`)
- `from` and `to` must be UTC dates (not timestamps)
- `to` cannot be before `from`, and cannot be after today UTC
- `to` may equal today (partial day, returns up-to-the-minute counts)

## Response format

`200 OK` — JSON body:

```json
{
  "ssp": "example-ssp",
  "from": "2026-10-25",
  "to": "2026-10-27",
  "currency": "USD",
  "timezone": "UTC",
  "days": [
    {
      "date": "2026-10-25T00:00:00Z",
      "bidCount": 14523,
      "winCount": 8234,
      "billCount": 7812,
      "impCount": 7980,
      "revenue":    { "byImp": 15.96, "byBill": 15.624 },
      "averageCpm": { "byImp": 2.0,   "byBill": 2.0 }
    },
    {
      "date": "2026-10-26T00:00:00Z",
      "bidCount": 16002,
      "winCount": 9015,
      "billCount": null,
      "impCount": 8721,
      "revenue":    { "byImp": 18.3141 },
      "averageCpm": { "byImp": 2.0999999999999996 }
    },
    {
      "date": "2026-10-27T00:00:00Z",
      "bidCount": 0,
      "winCount": 0,
      "billCount": null,
      "impCount": 0,
      "revenue":    { "byImp": 0.0 },
      "averageCpm": { "byImp": 0.0 }
    }
  ]
}
```

### Top-level fields

| Field | Type | Meaning |
|---|---|---|
| `ssp` | string | Your SSP id (echo of the path variable) |
| `from`, `to` | string | UTC date range `YYYY-MM-DD` (echo of the query params) |
| `currency` | string | Always `"USD"` |
| `timezone` | string | Always `"UTC"` |
| `days` | array | One entry per UTC day, ascending |

### `days[]` fields

| Field | Type | Meaning |
|---|---|---|
| `date` | string | Start of the UTC day, ISO 8601 with `Z` suffix, e.g. `2026-10-25T00:00:00Z` |
| `bidCount` | integer | Bids RevoSurge returned to your SSP |
| `winCount` | integer | Win notifications received from your SSP |
| `billCount` | integer \| `null` | Billing notifications received from your SSP. `null` when none were received that day, or when bill data is temporarily unavailable — treat as unknown, not zero |
| `impCount` | integer | Impressions recorded by our impression pixel, deduplicated per impression and counted on the day the impression fired |
| `revenue.byImp` | number | Sum of winning bid prices for recorded impressions, USD (CPM ÷ 1000 per impression). Rounded to 4 decimals |
| `revenue.byBill` | number (optional) | Sum of winning bid prices for billed impressions, USD. Rounded to 4 decimals. **Omitted** when `billCount` is `null` or bill revenue cannot be computed |
| `averageCpm.byImp` | number | `revenue.byImp × 1000 ÷ impCount`, USD. `0` when `impCount` is `0` |
| `averageCpm.byBill` | number (optional) | `revenue.byBill × 1000 ÷ billCount`, USD. **Omitted** whenever `revenue.byBill` is omitted |

Days with zero activity are still present (counts = 0, `billCount` = `null`,
no `byBill` keys) so the array always has `(to - from + 1)` rows. Caller
iterates without gaps.

::: warning Parse `byBill` as optional
When there is no bill data, the `byBill` key is absent from `revenue` and
`averageCpm` (it is not sent as `null`). Treat a missing `byBill` the same as
`null`.
:::

### `byImp` vs `byBill`

Revenue and CPM are reported on two independent bases:

- **`byImp`** — based on impressions our pixel recorded. Available for every SSP.
- **`byBill`** — based on billing notifications your SSP sent us.
  Only present if your SSP fires billing notifications. Revenue covers the
  bills we can match to a winning bid, so it can be slightly lower than
  `billCount` × your clearing price.

Reconcile on the basis that matches how you bill: `byBill` if you send
billing notifications, otherwise `byImp`.

`averageCpm` values are not rounded (e.g. `2.0999999999999996`); round on
your side if needed.

## Example call

```bash
curl "https://rtb.revosurge.com/api/v2/ssp/example-ssp/report?from=2026-10-25&to=2026-10-27" \
  -H "Authorization: Bearer <your-token>"
```

Same call with the token in the query string:

```bash
curl "https://rtb.revosurge.com/api/v2/ssp/example-ssp/report?from=2026-10-25&to=2026-10-27&access_token=<your-token>"
```

## Rate limit + caching

- **10 requests/minute** per token. Exceeding returns `429`.
- Identical `(sspId, from, to)` queries are **cached for 5 minutes** server-side.
  Repeated queries inside that window do not hit the warehouse.
- Recommended polling cadence: **once per hour or less**. Daily totals
  don't change after the day closes.

## Errors

| Status | `error` | Cause |
|---|---|---|
| `400` | `bad_date` | `from` or `to` is not a `YYYY-MM-DD` date |
| `400` | `bad_window` | Window > 7 days, `to` before `from`, or `to` after today UTC |
| `401` | `unauthorized` | Missing token, bad signature, wrong issuer, or token's `sub` ≠ path `{sspId}` |
| `429` | `rate_limit_exceeded` | More than 10 requests/minute for this token |
| `500` | `internal_error` | Internal error — retry after a short delay |

Error body shape:

```json
{ "error": "bad_window", "detail": "window exceeds 7 days (got 14)" }
```

`detail` is present on `400` and `401` responses only.

## How to obtain a token

Reach out via your **existing communication channel with RevoSurge**
(Telegram, Microsoft Teams, or whichever channel you already use with your
account manager) and share your SSP id. We will:

1. Verify your identity and the SSP you operate.
2. Sign a long-lived JWT with your SSP id as the `sub` claim.
3. Deliver the token and your report URL back through the same channel.

Treat the token like a password:
- Do not commit it to source control.
- Store it in a secrets manager or environment variable.
- Restrict access to engineers who need to call the API.

## Token rotation

If we rotate the signing secret (e.g. after a suspected leak):

1. All existing tokens stop working immediately. You will receive `401` on
   every request.
2. RevoSurge will issue you a fresh token via the same channel as the
   original delivery.
3. Replace the old token with the new one in your environment.

To request rotation proactively (e.g. you suspect your token has been
exposed), notify us through the same Telegram / Teams channel you used
to receive the original token.

## Migrating from v1

The v1 endpoint (`/api/v1/ssp/{sspId}/report`) is no longer publicly
available. Your existing token works on v2 unchanged. Field mapping:

| v1 | v2 | Notes |
|---|---|---|
| — | `timezone` | New, always `"UTC"` |
| `days[].date` (`2026-10-25`) | `days[].date` (`2026-10-25T00:00:00Z`) | ISO 8601 with `Z` |
| `days[].bids` | `days[].bidCount` | |
| `days[].wins` | `days[].winCount` | |
| — | `days[].billCount` | New |
| `days[].imps` | `days[].impCount` | |
| `days[].totalCpmUsd` | `days[].revenue.byImp` | Different basis — see below |
| — | `days[].revenue.byBill`, `days[].averageCpm.*` | New |

v2 `revenue.byImp` is calculated on a different basis from v1
`totalCpmUsd`, so historical v1 figures will not match v2 exactly.

## FAQ

### Why are my bid, win, bill and impression counts different?

Four counts are returned for transparency:

- **bidCount** — bids RevoSurge returned (you may have rejected them in the auction).
- **winCount** — win notifications you sent us (auction confirmation).
- **billCount** — billing notifications you sent us.
- **impCount** — impressions recorded by our impression pixel.

These can diverge by a few percent:
- *Wins > imps* if the impression pixel doesn't fire (creative blocked, ad-blocker, network).
- *Imps > wins* in rare retry / multi-imp scenarios.
- *Bills ≠ imps* depending on when your SSP fires the billing notification.

### Which traffic does my SSP id cover?

- If your SSP id contains a `-` (e.g. `acme-banner`), the report covers
  **exactly** that id.
- If it does not (e.g. `acme`), the report covers that id **plus every
  descriptor that starts with it followed by `-`** (`acme-banner`,
  `acme-pop`, …). This lets one token cover all your variants.

If you require a different breakdown, contact us.

### How fresh is the data?

- **Bids, wins and bills** appear within seconds of the event.
- **Impressions** appear within seconds of the impression-pixel event.
- **Late-arriving notifications** (delayed by the SSP) can shift counts by
  ~1% within the first 1–2 hours after midnight UTC. Counts stabilize after
  that.

### Can I query more than 7 days at a time?

No. Issue multiple requests for adjacent 7-day windows. The 5-minute cache
makes this efficient if you run a daily backfill job.

### Currency

All revenue and CPM values are USD. We do not convert to other currencies.
